| 维度 | 结论 |
|------|------|
| **场景** | 政务内网 B 端工作台（Web 桌面端，min-width 1280px），单文件高保真原型；编辑器型主视图 + 多管理型视图 |
| **受众** | 南京江北新区管委会：合同经办人（拟制/修订/导出）、法务治理中心（模板/条款/规则维护）、预审人员（疑点处理/报告）、领导层（统计看板）。非技术用户，偏好「按钮即结果」的确定性交互 |
| **调性** | 政务庄重风 = Tech Utility × Modern Minimal 混合：政务蓝主色（#0E4C92→#13A8A8 渐变）、中性灰底、公文式正文排版（宋体/仿宋感）、等宽数据表格、AI 辉光点缀（--ai-glow）。已有完整 CSS 变量设计令牌，**必须沿用不另立风格** |
| **品牌上下文** | 已有强品牌资产：与同平台「辅助文本合规审查」统一视觉体系；设计令牌（--primary/--ai-navy/--ai-cyan/阴影/圆角 9px/按钮 34px 高等）已在 :root 固化。新视图须复用 `.card/.tbl/.kpi/.btn/.select/.modal/.toast` 等既有组件类 |
| **规模** | 现有 6 个视图（编辑器/历史与版本/统计报表 + 模板/条款/规则三库以共享资料库视图承载）。扩展后预计 **12~14 个视图**：现有 6 + 预审模块新增 6~8（法规库、依据管理、模型构建器、项目库、作业与报告、AI 工具、管理工具、比对工具、识别工具可合并为 6 个视图），加上若干弹窗/抽屉。交互复杂度：静态展示 + 演示级动效（进度条、打字机、diff 高亮），无真实后端 |

## 三、信息架构建议

### 现状问题
现有原型**没有全局功能导航**——左侧栏是「草稿列表」而非菜单；模板/条款/规则三库无独立 view 容器（仅以共享资料库结构 + `viewJump` 从预审面板链接进入），历史/统计靠 `switchView` 硬编码切换。新增 9 个预审子模块后必须建立**两级分组导航**。

### 推荐导航树（左侧栏改为「功能导航 + 草稿列表」上下两段，或功能导航置顶栏）

```
合同智能生成及预审
├── 工作台
│   ├── 合同拟制（编辑器·现有 view-editor）
│   └── 统计分析（现有 view-stats）
├── 智能生成（资料库组）
│   ├── 合同模板库（现有，增强生命周期操作）
│   ├── 合同条款库（现有）
│   └── 预审规则库（现有）
├── 智能预审（全新组）
│   ├── 预审作业与报告 ★（预审主入口，含疑点/报告/归档）
│   ├── 预审模型配置（拖拽构建 + 模板库）
│   ├── 法律法规库（知识图谱 + 版本对比）
│   ├── 预审依据管理（效力等级 + 审核入库）
│   └── 预审项目库（专题库 + 穿透查询）
├── 智能工具（全新组）
│   ├── 预审工具箱（多模态导入/图片比对/合同图价识别 三 Tab）
│   └── AI 工具管理（文本处理/OCR/预审专用 三分类）
└── 台账
    └── 历史与版本（现有 view-history）
```

实现要点：
- 左侧栏顶部保留「新建合同」按钮；功能导航插入搜索框与草稿列表之间（可折叠分组）；草稿列表仅在「合同拟制」视图下显示，切到其他视图时整栏换为导航（或草稿列表折叠到底部）
- 每个全新视图复用现有骨架：`.page-scroll > .page-head + .card + .tbl`，三库式「左分类导航 + 右表格」模式可复用于法规库/依据库/项目库
- 预审作业与报告为预审模块主入口，与「合同拟制」形成生成↔预审双主线

## 四、关键交互流程建议（核心用户旅程）

### 旅程 1：合同拟制 → 预审 → 导出（已有主链路，保持不变）
经办人「新建合同」→ 三步向导录入要素 → 智能匹配生成草案 → 四维预审（采纳/忽略逐条处理）→ 保存版本留痕 → 导出草案+预审报告 → 提交法务复核。预审面板问题卡可「查看依据」跳转法规库对应条款，串联新旧模块。

### 旅程 2：发起专项预审作业（全新）
预审人员进入「预审作业与报告」→ 新建作业 → 上传合同或从项目库选取数据 → 选择预审模型（或跳「模型配置」临时调整）→ 系统跑出疑点清单（每条疑点展示关联法规依据链，可穿透到法规库原文）→ 人工确认疑点 → 一键生成预审报告 → 分类归档，作业状态同步至台账。

### 旅程 3：法务治理中心维护知识资产（增强）
法务人员进入「合同模板库」→ 上传新版模板 → 系统自动解析标签化 → 发起生效审批（旧版自动作废并留存历史时间线）→ 变更记录写入留痕视图；同理维护条款库、规则库、法规库（修订需审批、历史版本可 diff 对比）。旅程终点可通过「统计分析」查看规则命中趋势闭环。

## 五、给下游阶段的提示

- **设计系统（Phase 2）**：直接提取 contract.html `:root` 令牌为 DESIGN.md，无需新建风格；新增组件需求：知识图谱节点、拖拽画布、双图比对器、仪表盘评分环
- **原型构建（Phase 3）**：建议拆分为「增强现有 contract.html」+「预审模块新视图」两批，优先做旅程 2 全链路（预审作业→模型→依据→法规→报告）作为演示主线
- **风险点**：9 个全新模块信息量大，单文件 HTML 行数可能超 4000 行，建议按视图模块化组织 script；知识图谱与拖拽构建器用演示级实现（SVG 静态 + 点击添加），不做真实引擎
